# pi-project-memory 开发规则

本文件是项目的详细开发规则。根目录 [AGENTS.md](../AGENTS.md) 是每次会话的入口，
只放硬性上限；具体流程、契约和验证分级在这里。当前代码、测试与用户明确要求优先于历史文档。

## 1. 开工顺序

按任务挑选，不要把所有文档都读一遍：

| 任务 | 先读 |
|---|---|
| 任何改动 | 已注入的根 `AGENTS.md` 不重读；看 `git status`，再按需定位相关源文件与测试 |
| 功能/契约变更 | [README](../README.md) 对应小节、`src/memory.mjs`、`src/recall.mjs` 与直接相关测试 |
| 旧数据边界 | [格式与升级边界](../docs/migration.md) |
| 测试与验收 | [测试说明](../docs/testing.md)、`test/` 下对应文件 |

README 与 `docs/testing.md` 都属于大文件，按第 2 节定点读取。

## 2. 读取与上下文预算

目标：不靠"整文件读入"建立理解，也不为了一个符号读 30 KB。

### 2.1 分档

| 体量 | 做法 |
|---|---|
| < 8 KB | 可以一次读完 |
| 8–32 KB | 先取结构（标题/导出/函数签名），再读 1–3 个区间，每次 ≤ 200 行 |
| > 32 KB 或生成/数据文件 | 只允许定点检索；`test/fixtures/`、`*.jsonl`、日志不整读 |

- 单次 `read` 最多 200 行或 8 KB，必须显式 `limit`，需要时用 `offset` 续读。
- 估算体量：`wc -c f`；排序：`find . -path ./.git -prune -o -type f -printf '%s %p\n' | sort -rn | head -20`。

### 2.2 结构优先的常用命令

```bash
grep -n '^#\{1,3\} ' README.md                     # Markdown 目录
rg -n '^(export |async function |function |class |const [A-Z_]+ ?=)' src/memory.mjs
rg -n -C 3 'normalizeNote' src test                # 定义 + 调用点
sed -n '120,200p' docs/testing.md                  # 指定区间
git diff --stat && git diff -- src/cli.mjs          # 只看需要的文件
```

### 2.3 Pi 宿主与第三方包

- 默认**不读** `node_modules/**` 和
  `<Pi 宿主安装目录>/**`。
- 只有任务直接涉及 Pi API / 宿主行为时才查宿主文档；先定位一个相关主题，再按上级指令
  读取对应文档与必要引用，不把文档链接当作遍历清单。本地业务/存储改动不默认研究 Pi。
- 文档路径先验证存在；不要猜文件名，也不要为寻找路径递归扫描宿主包。
- 只有在文档确实缺失、且结论必须依赖实现细节时，才对该包做**单文件定点** `rg -n -C 3`，
  并在交付报告里写明读了哪个文件、为什么必须读；不要顺手把整包读一遍。
- 第三方/上游行为要有出处，引用为路径或"文档小节"，不要凭印象写 API。

### 2.4 输出纪律

- bash 输出加约束：`head`、`tail`、`sed -n`、`rg --max-count`、`git diff --stat`、`--name-only`。
- 默认不重复读本次会话已读过的区间（例外见 2.6）；不复述整段 diff 或完整日志，只引用关键行。
- 部分阅读时明确说明"只看了 X 到 Y"，不要把局部内容当作全文结论。

### 2.5 累计预算与停止条件

- 一个任务只解决一个明确目标。先确定待回答的问题和候选文件，再检索；每次读取必须能
  回答具体问题。禁止为了“熟悉项目”遍历仓库、历史记录、宿主或全部测试。
- 每轮探索（从开始定位到首次编辑/验证，或一次明确的新问题定位）累计正文输出上限为
  **64 KB / 16 个不同文件，先到者停**。`read`、bash、网页、子代理返回内容合并计入；
  并行、分段、换工具不重置预算。无法精确计量时保守估算，不声称有自动计量器。
- 每 **3 次探索工具调用**检查一次：是否已能编辑或回答？能则停止读取；不能则收窄问题。
  超预算前先用不超过 5 行说明已知、缺口与最小追加范围，取得用户确认再扩展，不能自行重置。
- 已有实现、调用点和相关测试足以确定契约时，就停止探索并做最小改动；无关层次不继续追踪。
  仅改规则/文档时不读业务实现、不跑代码全量测试。
- 搜索只覆盖候选文件/目录；无目标时允许一次文件名定位（排除 `.git`、`node_modules`、
  产物目录），随后收窄。单条命令返回最多 **80 行 / 8 KB**，取较小者；超出时改查询，
  不反复翻页。测试保留失败摘要与关键栈，成功只保留统计。
- 不因“更保险”追加全量测试、宿主源码阅读或多轮审查；这些必须有具体未解决风险。
  上级指令要求完整读取的文档仍须完整读取，但同样计入预算；不足时先申请扩展。

### 2.6 长对话与交接

- 同一对话不无限串联开发目标。当前目标完成后，若新请求是独立功能/架构方向，或已出现
  上下文压缩、明显重复调查，先建议新开对话；用户选择继续时，不重复加载整套背景。
- 交接摘要最多 **30 行**：目标、已确认结论及路径/符号、已改文件（区分原有用户改动）、
  实际验证、未决问题、下一步。不要粘贴原始对话、代码、diff 或完整日志。
- 默认直接给摘要，不自动创建文件或写入记忆；用户要求落盘时再写到指定新文件。
  本仓库没有 `.pi-root`，不能为交接创建标记或改用全局记忆。
- 新对话只加载摘要和下一步所需区间；摘要是导航，不替代当前文件证据。已读内容不重复读，
  除非文件已变更、证据已不在可用上下文或需核验精确文本；此时只读最小相关区间。
- 规则只能约束后续行为，不能清除已有上下文；不宣称已自动压缩、重置会话或降低实际 token。

## 3. 架构与所有权

只有一套实现，用户概念只有当前状态与长期笔记：

| 路径 | 职责 |
|---|---|
| `index.ts` | 唯一 Pi 扩展：命令、两个工具、每次模型调用前刷新上下文 |
| `src/memory.mjs` | 项目边界、文件格式、原子写入、冲突保护、上下文预算 |
| `src/recall.mjs` | 从有效笔记重建内存稀疏 TF-IDF 向量，以余弦相似度检索 |
| `src/cli.mjs` | CLI 与有界 JSON 输入 |
| `bin/pi-project-memory.mjs` | 唯一可执行入口 |
| `examples/` | 可读笔记示例，不是运行时配置 |

必须保持的契约：

- 没有 `.pi-root` 就不启用记忆；标记只能由用户显式 `/memory-init` 或 CLI `init` 创建。
- 新格式只使用 `.pi-memory-local/`，旧配置和记忆不读取、不修改、不自动迁移。
- `state.md` 与 `notes/<uuid>.md` 是内容的唯一权威来源，没有事件链或投影视图。
- 新增原子独占发布；修改与失效必须持有锁并匹配当前文件内容哈希，再原子替换。
  不自动解除崩溃锁，不静默吞掉手工修改或并发冲突。
- `active` 才参与默认笔记召回；`unverified`、`inactive` 需显式查询。
- 上限集中在 `src/memory.mjs` 的 `LIMITS`；默认上下文最多 12000 字符，整条放入或省略。
  向量只在内存重建，不能另存一份事实或让过期索引恢复失效笔记。
- 路径必须通过逐级检查，禁止存储内符号链接逃逸；错误统一为 `MemoryError`。
- 不把记忆当授权，不把引用存在当结论正确；科学适用条件、来源、单位和失败性质保存在正文中。
- 工具/CLI 契约变更必须同步 README 与直接相关测试。不重新引入候选、审核、投影或后台治理。

## 4. 修改约定

- 小步、定点：不重构无关代码，不新增依赖或构建步骤，不顺手换风格。
- 复用 `src/memory.mjs` 与 `src/recall.mjs` 中的校验、存储、检索原语；确认实际定义后再调用，不要凭名字猜签名。
- 缺失、未知与非有限值要显式处理，不能当 0 或空串；涉及数值/字节上限时写清单位。
- 时间是外部输入时避免不必要的不确定性；不要为了测试通过削弱校验。
- 所有已有改动视为用户工作，不回退、不覆盖。有 `.git` 时先检查 `git status`；无 `.git` 时记录文件基线，不为检查状态自动初始化仓库。
- 版本号、`package.json` 的 `files`/`bin`/`pi` 字段只在用户要求时改动。

## 5. 验证分级

按影响面选择，从最小开始，逐级上升：

1. `node --check` 目标文件；`npm run check` 覆盖全部入口与 `src/*.mjs`。
2. 定向单测：`node --test test/<name>.test.mjs`。
3. 全量：`npm test`（`node --test test/*.test.mjs`）。宿主相关用例需要
   `PI_TEST_HOST_PACKAGE=<宿主 package.json>`，未设置时按跳过处理，报告里说明。
4. 完整宿主/TUI 验证不在现行测试套件内；只有具体交互风险需要时，另行设计隔离检查。

约束：

- 测试写入新建临时目录，结束后清理；不得改动用户真实记忆包、`~/.pi`、`~/.bashrc`。
- 入口测试只加载调用者明确指定的已安装宿主 API，不启动真实模型或正常工作会话。
- 合成 fixture 通过不等于真实宿主兼容或科学正确；不要用它们声称宿主验证完成。
- 报告必须写清：实际执行的命令、通过项、跳过项、未验证项。

## 6. 交付报告

- 范围：改了哪些文件、为什么。
- 验证：跑了什么、结果、跳过与原因。
- 契约影响：CLI/工具/schema/存储是否有可观察变化；没有就写明没有。
- 限制：未验证部分、依赖宿主的假设。
- 不宣称做过的事：没有提交、没有推送、没有安装依赖、没有跑真实模型或计算。

## 7. 环境

- Node.js >= 22.19（与 Pi 1.2.0 一致），ESM；包管理器即 npm，无构建产物。
- 宿主包由外部 Pi 安装提供，不假定用户名、安装前缀或全局 npm 布局；
  宿主检查使用调用者提供且已验证存在的 `PI_TEST_HOST_PACKAGE`（宿主 `package.json` 绝对路径）。
  不要在仓库内安装或升级它。
- 调试脚本用 `node --input-type=module` 或临时目录内的 `.mjs`，不要把临时脚本提交进仓库。
