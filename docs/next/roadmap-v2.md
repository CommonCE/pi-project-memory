状态：根据本轮长期记忆架构讨论重新安排。M1–M3 已实现，M4 冻结在离线契约，M5/M6 已完成本地契约验收，M7 部分完成。这里的进度来自现有阶段文档，不是本轮重新测试的结论。
本文是当前优先级入口；总体边界见 [架构与项目盘点](architecture.md)。替代旧路线中“简化 M7 后直接进入使用质量与发布”的单一路径，但不扩张当前 M7 的实施范围。

## 1. 目标与不变项

面向科研计算、软件开发、集群操作等长期项目，实现“记住—找回—继续—纠正”。先保证项目内闭环可信，再逐步补准入、证据与更新治理，不追求全自动记忆。

- 默认仍为 v1 `index.ts`；v2 显式加载 `v2.ts`，两者不同时加载。
- 保留 `.pi-root` 显式启用、scope 祖先继承与兄弟隔离、原子独占写入、修订恢复、手改保护和候选发布保真。
- 保留科研单位、未知/失败限制、固定来源修订；正常结束、收敛、科学有效不能互相推出。
- 记忆不构成当前计算、提交或其他执行授权。
- 不自动迁移旧 pack，不改变版本、默认入口、打包字段，不提交、推送或重写历史。

2. T2 已完成本地核对：修复同会话目录/项目切换、切回及离开项目再切回的简报资格；规范化别名、会话切换/fork、取消、失败重试和压缩归属通过定向测试。未改写生命周期框架。
3. T3 已完成合成闭环：保存→找回→新会话续接→同 ID 显式纠正，固定失败来源、单位和旧权威记录字节不变；未执行实际计算。

## 4. P1：小规模使用验收与缺陷收敛

P0 之后先取得使用质量证据，而不是直接扩建系统。

当前进度：已完成本轮三类合成短流程与局部缺陷收敛，见 [P1 计划/结果及问题清单](p1-acceptance.md)。最终定向 43 通过、0 失败、1 宿主适配跳过；修复首轮简报截短 blocker 后状态详情未补回的上下文省略问题。真实 Pi 会话、模型、项目和人工科学审阅未验证，不能据此宣布真实使用验收通过或进入 P2；不自动开始 P2 或发布。

- 先用隔离材料覆盖科研续接、软件开发续接、集群故障经验三类短流程；不执行科学计算或提交作业。
- 观察找回了什么、遗漏什么、是否越界、是否混淆版本/运行、是否带上必要限制。
- 记录注入长度、重复候选、审核负担、提炼调用成本；允许零候选。
- 真实 Pi 会话、真实项目数据及真实模型分别取得相应授权；没有授权时停在本地证据层级。

产物：问题清单、优先级、实际来源与验证范围。只有明确缺陷进入修复，不为完善指标扩大 M4 矩阵。
完成标准：能区分“检索漏记”“来源选择错”“状态过期”“上下文省略”“候选质量差”等问题，而不笼统归因于记忆不足。

## 5. P2：最小长期治理与 consolidation

这是下一轮设计主线，不是已批准的接口或 schema 变更。先按 P1 问题拆分小任务，再确认契约后实现。

### G1：准入与类型边界

统一 fact、decision、preference、procedure、problem/solution、pending 的语义，先映射既有记录与卡片，不批量重分类旧数据。
区分审核接纳、证据性质、适用性与运行有效性。保留显式保存和默认 review。

### G2：更新与证据缺口

复用修订与固定来源，明确补充、纠错、环境演变和未解决冲突的处理。先区分不同适用范围，不采用最后写入者获胜。
盘点原始来源可访问性与现有摘录覆盖；只对实际缺口设计证据失效提示或最小身份保留，不默认复制完整会话和大文件。

### G3：显式或里程碑式 consolidation

先提供可审查的整理过程：新增信息→与已有知识比较→去重/冲突检查→少量候选→接纳。不直接自动改写正式知识。
明确 Working 交接与长期沉淀的区别，允许零产出，防止旧摘要成为新证据。
之后再评估是否将现有按回合提炼调整为有意义变化触发；必须比较漏记、费用和审核成本，不能先改默认行为。

完成标准：同一信息不会反复入库；改口或环境改变有解释；pending 能退出活跃视图；关键结论能回到依据；整理不会把助手建议提升为事实。

## 6. P3：按实际瓶颈改善召回与上下文

- 以项目/scope、主题、实体和现有全文搜索为基础，增加确实有用的少量关系与有界展开。
- 明确 Inline 最小自足结论与 Spill 入口，保留版本、单位、适用条件及不确定性。
- 只有跨措辞漏召回成为实际问题时，才评估 embedding 候选补充；不把向量相似度当作有效性判断。
- 使用固定问题与人工审阅比较正确恢复、越界/过时召回、上下文开销和停止条件。

完成标准：相同预算下改善有依据的召回，不为了覆盖率注入更多无关记忆。不预先建设通用知识图谱。

## 7. P4：跨项目提升与可复用流程（可选）

只有多个项目已积累明确重复价值后才启动：

- Global 先保持少量显式偏好、通用约定与流程入口；项目知识不自动升为全局。
- 项目与共享环境的适用范围明确，跨项目检索单独控制。
- problem/solution 多案例比较后才形成 procedure；procedure 经验证和审查后才形成 Skill 提案。
- 不自动创建/改写 Skill，不复制 AGENTS.md 或项目文档形成平行规则源。

启动条件不是“前面任务做完”，而是实际复用需求足以支付维护成本。

Git/远端操作、默认入口切换、打包与版本变更均需单独授权。发布不是所有未来能力都实现，也不能以本地测试替代真实使用证据。审计入口见 [公开前清理审计](publication-audit.md)。

## 9. 后置事项与重启条件

| 事项 | 何时再讨论 |
|---|---|
| 目录迁移 | 真实改名频繁且明显影响召回；需分别考虑知识、事件、state 与候选 |
| 专门冲突中心 | 现有拒绝与诊断确实不能定位冲突 |
| 审核过滤与复杂 UI | 候选规模或跨目录混杂成为痛点 |
| 批量事务/恢复系统 | 已授权的具体批量操作确实需要 |
| 通用图谱、向量库或存储重建 | 现有结构在实际规模下出现明确瓶颈 |
| 全自动 consolidation/Skill | 有足够可靠案例、验证机制与维护责任后再评估 |

不设统一 TTL、综合可信度分数或记忆条数增长目标，不后台扫描全部历史会话，不因路线图存在而授权以上功能。
